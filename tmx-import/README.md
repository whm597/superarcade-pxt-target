# SuperArcade 编辑器：导入 Tiled 瓦片地图（.tmx/.tsx → 资产）

## 这是什么

在 SuperArcade 定制 MakeCode Arcade 编辑器中新增「导入 Tiled 地图」功能：
- 顶部工具栏「导入图片」按钮右侧新增按钮 **「导入Tiled」**（固定右上角，与「导入MIDI」同排）
- 选择 Tiled 工程文件（`.tmx` 或 `.tmj` 地图 + `.tsx`/`.tsj` tileset 定义 + `.png` 瓦片图片）
- 解析转换后 **直接写入编辑器资产管理器**（瓦片 tile 资产 + 地图 tilemap 资产），无需手动粘贴 jres（编辑器内 jres 是只读文件，粘贴不通，所以做成按钮直接入库）

## 安装（增量包 delta-tmx-import-v85.zip，v8.5）

1. 解压 `delta-tmx-import-v85.zip`
2. 将 `resources/` 目录整体覆盖到编辑器安装目录（与 `resources/app/` 合并，即用包内的 `resources/app/editor/target.js` 和 `resources/app/inject/inject.js` 覆盖同名文件）
3. 重启编辑器

> 包内含：
> - `resources/app/editor/target.js` —— v11.3 存档修复版基准（本次未改动，仅为完整结构，MD5 `1ddcb992939ee3240494f1e05ddee7ef`）
> - `resources/app/inject/inject.js` —— 含 TMX 导入模块（原版 61KB + 新模块，前 1294 行与原版逐字节一致，合并版 MD5 `906a9f172f0317ebc740de8249c66a94`，113563B）

## 使用方法

1. 打开编辑器，顶部工具栏「导入图片」按钮右侧出现 **「导入Tiled」** 按钮
2. 点击按钮 → 选择文件（可多选）：
   - 必需：地图文件 `.tmx`（XML）或 `.tmj`（JSON）
   - 可选：tileset 定义 `.tsx`（XML）或 `.tsj`（JSON）——若 tmx 里是**外部引用**（`<tileset source="...">`）则必须同时选择
   - 必需：tileset 图片 `.png`
3. **弹出「选择目标瓦片尺寸」对话框**：
   - 显示**原尺寸**（如 `40px × 40px`）
   - 提供**像素输入框**（默认 16）与 4/8/16/32px 快捷按钮
   - Arcade 编辑器/运行时只支持 **4 / 8 / 16 / 32px**（这是 pxtlib 的硬编码枚举，无 20/24/40 等中间值）；非标准尺寸（如 40px）必须缩放后才能在地图编辑器使用
   - 缩放为**面积平均（box 滤波）重采样**（保留像素风与砖缝等 1px 细线），瓦片与地图同时缩放、格数引用同步换算
   - 输入非法尺寸会红字提示，点「取消」放弃导入
4. 导入成功提示：`瓦片 N 个（图集全量），地图用到 M 种` + `地图资产：level1` + 缩放说明
5. 到「资产」面板查看；打开地图资产后，**瓦片会出现在地图编辑器的 My Tiles 中**（只有选中/打开地图后 My Tiles 才加载该地图用到的瓦片集合）

只导 tileset 不导地图也可以：只选 `.tsx` + `.png`，同样会先弹缩放对话框，再把 tileset 里**所有 tile** 导入为瓦片资产。

## 支持范围

| 项目 | 支持 |
|---|---|
| 地图格式 | Tiled 正交（orthogonal）地图，`.tmx` XML / `.tmj` JSON |
| tileset | 外部引用（.tsx/.tsj）与内嵌 tileset；多 tileset 自动按 firstgid 合并 |
| 瓦片尺寸 | 正方形 tile；导入时可选择目标尺寸 4/8/16/32px（原尺寸非标准则强制缩放） |
| 图层数据 | CSV、base64、base64+zlib、base64+gzip；无限地图（chunk） |
| gid 处理 | 自动紧凑重映射（1..N），透明像素 → 透明 tile |
| 颜色转换 | PNG → Arcade 16 色调色板（最近色匹配，半透明按透明处理） |
| 瓦片导入 | **全量导入**：图集所有瓦片全部入库（含地图未用到的） |
| 上限 | 瓦片资产数无上限（如 20×20=400 全量导入）；仅「地图用到的瓦片种类」受 Arcade 数据区索引上限 255 约束 |

## v8.5 修复内容（对应 v8.4 实测的新问题：云朵上半部分露出透明空洞）

### 背景空洞（Arcade 单层瓦片无图层叠加）—— 已修复
- **现象**：v8.4 实测瓦片全部匹配正确，但**云朵等瓦片内部未 100% 填充的部分露出透明空洞**（如云朵上半部分），原图里这些透明区域是由天蓝背景补充的
- **根因（Arcade 与 Tiled 的机制差异）**：Tiled 是**多图层叠加渲染**——background 层天蓝铺满（3520 格 gid85）+ scene 层云朵盖在上面 → 云朵瓦片内的透明像素透出下层天蓝，显示为"云朵嵌在蓝天里"。**MakeCode Arcade 的 tilemap 是单层瓦片索引**：一个格子只能存一个瓦片，云朵格子被云朵瓦片独占，瓦片内透明像素（f4 值 0）渲染时透出的是**地图底色**而非背景层 → 空洞
- **修复（导入时模拟背景层）**：convert 合并各图层后统计 gid 出现次数，**覆盖 >50% 格子的 gid 视为背景层**（本素材 gid85 天蓝）；把**地图用到的瓦片**的透明像素（boxAvg 结果为 0 的像素）**填成背景瓦片的平均色**（天蓝 rgb(95,151,255) → 调色板最近色 9 浅蓝，与背景瓦片显示一致）→ 云朵/山丘的透明部分在编辑器与游戏里都显示为背景色，不再空洞
- **边界**：仅对"地图用到的瓦片"填充（资产面板中未用到的瓦片保持原样）；未检测到明显背景层（无 >50% 的单一 gid）时跳过填充，行为与 v8.4 一致
- **验证**：
  - 云朵瓦片 tile360-362/tile380-382：**透明像素 0 个**（212/168/211/70/32/35 个像素填为天蓝，其余云朵主体保留）✓
  - 山丘瓦片 tile280-282：透明像素 0 个（透明部分填天蓝，山体保留）✓
  - 全地图 3520 个非 0 格子引用对照仍 **0 错误**；改名模拟回归通过；前 1294 行逐字节一致、node --check 通过、target.js 未改

## v8.4 修复内容（对应 v8.3 实测的新问题：白云、山丘仍错配成别的瓦片）

### gid > 255 被 Uint8Array 截断 —— 已根治（云朵/山丘错配的真正根因）
- **现象**：v8.3 实测（FC 马里奥 1-1）：**蓝天背景、底部 2 行红砖、金币都对了**，但**白云、山丘仍错配成别的瓦片**；瓦片名称仍是奇数（官方改名机制，与正确性无关）
- **根因（一字节 gid 溢出）**：convert 合并各图层到 `merged` 数组时用的是 **Uint8Array（0-255）**，而 Tiled 的 gid 可到 400（本素材）甚至更高。**gid > 255 的瓦片全部被截断成 `gid & 0xFF`**：
  - 云朵 gid **361** → 截成 **105** → 地图格子引用 gid105 的瓦片（错配）
  - 山丘 gid **281** → 截成 **25**；gid 381/382/383 → 截成 125/126/127…
  - 而背景 gid **85**、红砖 gid **81**、金币 gid **236** 都在 255 以内 → **不截断 → 显示正确**——完美解释"为什么只有白云/山丘错"
- **修复**：`merged`（和紧凑索引 `index`）由 **Uint8Array 改为 Uint16Array**，gid 完整保留（Tiled gid 高位翻转位已在解析时剥离，16 位足够）
- **验证（像素级）**：
  - 云朵：格子(85,1)(86,1)(87,1) = gid361/362/363 → 资产 **tile360/361/362** ✓；(85,2)…(87,2) = gid381/382/383 → **tile380/381/382** ✓
  - 山丘：gid281@(17,13)→**tile280**、282→**tile281**、283→**tile282**、301→**tile300**、302→**tile301**、305→**tile304** ✓
  - **全地图 3520 个非 0 格子引用逐一对照，错误 0**
  - 改名模拟回归（createNewTile 返回奇数 id）：仍全部正确；前 1294 行与原版逐字节一致、node --check 通过、target.js 未改

## v8.3 修复内容（对应 v8.2 实测的新问题：瓦片 ID 错配导致地图仍显示错乱）

### 瓦片 ID 错配（官方 createNewTile 自动改名 → 引用匹配失效）—— 已根治
- **现象**：v8.2 实测（FC 马里奥 1-1）：蓝天背景仍没还原、底部 2 排红砖显示为透明、白云/金币/天空蓝等瓦片错配（金币→火球、天空蓝→浪花）。**用户关键观察**：导入后的瓦片名称全是奇数（tile1, tile3, tile5…没有偶数），原 tsx ID 292 的旗子导入后叫 **tile585**——每个瓦片内容顺序与原文件对应、没有错位，只是名称间隔跳了一位（×2+1）
- **根因（官方 createNewTile 的 id 冲突改名 + v8.2 用 id 字符串匹配）**：官方 `TilemapProject.createNewTile(bitmap, id, displayName)` 的实现是 `id && !isNameTaken(id) || (id = generateNewID("tile"))`——**当传入的 id 已被项目占用时，官方自动改名为系统生成的编号**（用户项目里已有前几版导入的同名瓦片 → 本次全部冲突 → 名称变为奇数序列）。v8.2 的 tileset 对齐用"传入 id ↔ 返回资产 id 的字符串映射"，官方改名后**字符串匹配全部落空 → 回退全量顺序 tileset → 地图格子索引与 tileset 再次错位** → 背景/红砖/金币错配
- **修复（v8.3）**：`writeAssets` 的 tileset 对齐**不再依赖 createNewTile 返回的 id 字符串**——改为按**创建顺序**映射：`created[i]` 与 `result.tileAssets[i]` 一一对应（循环 push 顺序一致），引用列表用 convert 输出的 `ta.id`（连续 tileN）直接取到资产对象。**无论官方是否改名，地图引用都正确**。另加诊断日志：前 3 个瓦片打印"传入 id → 实际 id"，便于确认命名机制
- **验证**：
  - `test-inject-assets.js` 新增 **改名模拟场景**：FakeTilemapProject 模拟官方行为（忽略传入 id、返回 `myTiles.tile(2k+1)` 奇数命名，与用户实测 tile585 机制一致）→ 220×16 全部格子引用**仍正确**（用 displayName 对齐验证）
  - 正常场景（无冲突）：传入=实际 id，对齐断言全部通过
  - 真实 1-1.tmx 端到端回归：背景→tile84（天蓝）、底部→tile80（红砖）仍正确

## v8.2 修复内容（对应 v8.1 实测的新问题：导入的地图显示与原图不一致）

### 地图显示错乱（背景天蓝变没、部分瓦片被替换、底部红砖不对）—— 已修复
- **现象**：v8.1 实测（FC 马里奥第一关 1-1.tmx，220×16、40px、天蓝背景、底部红色地砖）：瓦片资产本身方向/比例/颜色都正常，但打开导入的地图后**背景蓝色消失、部分瓦片被相邻瓦片顶替、底部红砖不对**；16px 与 32px 导入都有此问题
- **根因（writeAssets 的 tileset 错位）**：瓦片资产按 **gid 全量顺序**写入（`tile0=gid1 … tile399=gid400`），而地图数据区格子索引是 **usedGids 紧凑重映射**（1..N，只含地图用到的瓦片种类）。`td.tileset.tiles = [透明] + 全量顺序资产`，格子索引 i 指向的是"全量顺序第 i 个瓦片"而非"重映射顺序第 i 个用到的瓦片"。**gid 不连续的瓦片全部错位**：如背景 gid85（天蓝）在紧凑索引里的位置 ≈ 40，但全量顺序 tileset 的 40 号位是 gid40 的瓦片 → 背景显示错误瓦片/透明；底部地砖 gid81 → 索引 39 → 全量顺序 39 号位是 gid39 的瓦片 → 红砖被顶替。连续 gid 段（如小号 gid）恰好对齐 → "大部分正常"
- **修复**：`writeAssets` 的 `tileset.tiles` 改为按**紧凑索引对齐**——取 `result.tilemap.tileset`（转换核心输出的"用到的瓦片引用列表"，顺序即重映射顺序 1..N），用 id 映射到已创建的瓦片资产，`tiles = [透明] + 对齐后的引用`；取不到引用时回退全量顺序并告警（不影响导入）。convert 输出的引用 id 为 `tileN`（无命名空间），createNewTile 后资产 id 为 `myTiles.tileN`，已做命名空间归一匹配
- **保留**：资产集合仍**全量 400 瓦片**（资产面板可查看全部）；只有地图的 tileset 引用表改为"用到的 N 种"（打开地图后 My Tiles 显示这 N 种）
- **验证**：
  - `test-inject-assets.js` 新增断言 3b：220×16 全部格子遍历，格子索引 i → `tileset.tiles[i]` 的 id 后缀 === `tileset 引用[i-1]`——**全部对齐**（模拟测试）
  - `test-repro-1-1-inject.js`（真实 1-1.tmx + map.png 端到端）：背景格子 → `myTiles.tile84`（gid85，**天蓝非透明 256/256，颜色索引 9**）；底部行 → `myTiles.tile80`（gid81，红砖纹理）；tileset=82（透明+81 用到的）、集合=401（全量 400+透明）——**真实数据落位正确**

## v8.1 修复内容（对应上一版实测的两个问题）

### 1）16px 导入瓦片失真（"垂直方向被拉长"）—— 已修复
- **根因**：40px→16px 是 2.5 倍**非整数倍**缩放，旧实现用最近邻采样（步长 2.5），1px 的砖缝/细线（黑线、白线）落在采样点之间被整行/整列跳过 → 视觉上横缝消失只剩竖缝（或反之），被感知为"垂直拉长/比例不协调"
- **修复**：改为**面积平均（box filter）重采样**——目标像素 = 源区域调色板颜色平均（跳过透明）再最近色量化，带边界保护。横竖细线都会保留
- **验证**：`test-tmx-scale.js`（40×40 源：砖色背景 + y=20 白横缝 + x=20 白竖缝 → 16px 输出横缝行/竖缝列 16 个非纯砖色像素、角落保持纯色）通过

### 2）32px（或 40px）导入的地图打开/引用时卡死（`Cannot read properties of undefined (reading 'id')`）—— 已定位并修复
- **根因（官方 tile-palette 组件 bug，与导入器无关）**：编辑器地图编辑器的瓦片调色板组件，打开地图时按 `瓦片.tileWidth === 地图.tileWidth` 从**内置 Gallery 瓦片**（硬编码 tileWidth=16）过滤分类。16px 地图 → 内置瓦片匹配 → 正常；32px/40px/4px/8px 地图 → 内置瓦片全部不匹配 → 4 个内置分类全空 → Dropdown 取 `C[0].id` 越界崩溃。**任何方式创建的 32px 地图在已加载过 Gallery 的环境下打开都会崩**
- **修复**：inject 层防御补丁——`Array.prototype.filter` 保底：当过滤结果为空且源是 tile-palette 的内置分类数组（首元素为 forest/aquatic/dungeon/misc 分类结构）时，保底返回首个分类，避免越界。16px 正常场景不受影响，原有功能不变
- **验证**：真实 pxtlib 数据往返（16px/32px trim + 渲染消费遍历均通过，证明数据层无问题）；崩溃点源码定位确认（`s.Forest=0`，`C[0].id`）

## 已知限制

- **图层合并**：所有瓦片图层按 Tiled 顺序合并（后画的覆盖先画的），暂不提供图层选择对话框
